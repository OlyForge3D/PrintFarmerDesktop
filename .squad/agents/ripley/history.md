## Learnings

- 2026-07-23: This repo's native Rust workspace lives at `native/` with `model-core` as the crate; `Cargo.lock`/`Cargo.toml` confirm Rust + SQLite integration is a first-class concern, not an afterthought — route any schema or FFI boundary work through Bishop with Vasquez reviewing concurrency implications.
- 2026-08-21: When a wizard has more visible buttons than the user guide has steps, cross-check the docs before assuming the extra button is the dispatch trigger. `CalibrationStepWorkflow.tsx:1420`'s "Start calibration print" has no `onClick`; the real dispatch is the "Confirm bed clear" button (`:1410`) invoking `acknowledgeCalibrationBedClear`. The user guide (`docs/printer-calibration-user-guide.md` §"Generate, queue, clear the bed, record the result") states the four-step flow as Generate → Queue → Confirm bed clear → Record; the extra button is a dead UI affordance, not a missing wire-up in the safety-critical path.
- 2026-08-21: A repo-wide grep for `mock|virtual|simulated|sandbox|dry-run|test-harness|stub` across `src/` is a fast test for "does the desktop have any non-production dispatch path?" — every hit in this codebase is renderer sandbox / partial-test-mocks / unrelated. A "mock printer" acceptance goal against a desktop with no mock-printer vocabulary is a **server-side ask**, not a desktop one; don't accept the framing as a desktop bug without first checking the vocabulary.
- 2026-08-21: The calibration dispatch gate chain in this repo has 25 discrete refusal points across 5 layers (availability negotiation, discovery, renderer context, action decision, main-process gate + sync prerequisites, HTTP + server, ack-bed-clear replay). When asked "why is dispatch refusing?", enumerate the gates in evaluation order and report the FIRST that fails — because the operator sees only the outermost message, and misdiagnoses cascade if you start at the HTTP layer without confirming G1-G5.
- 2026-08-21: `isExplicitCalibrationContextComplete` (`src/main/calibrationWire.ts:1245`) is the load-bearing predicate for every write action. It requires **every** identity field (profile, configuration, snapshot, orca profile, profileIdentities, at least one toolhead, slicerIdentity + slicerDistribution) to be populated. A server that returns a partial context — even one legal for read-only availability — will refuse every write action with a `contextIncomplete` gate reason. When Bishop investigates pfarm1, this is the single most likely failure surface.
- 2026-08-21: The desktop's `calibrationApiEnabled + calibrationChangeFeedEnabled + calibrationOfflineDraftEnabled` triad is a hard availability gate (`REQUIRED_CALIBRATION_FLAGS`, `calibrationWire.ts:1805`). All three must be advertised true for the workspace to open at all. Any mock-server stub needs to serve all three regardless of whether the mock actually implements the change feed or offline draft push — otherwise the workspace refuses before printer discovery even runs.
- 2026-08-21 Round 2: The Round 1 alias-triad prediction was empirically half-wrong. Live-stack `GET /api/calibration/capabilities` proved the desktop's three internal flags do not map to a shared `calibrationSyncEnabled` doublet — they map to three **distinct** fields, and one (`calibrationOfflineDraftEnabled`) is nested under `operatorFeatures`. When the flat top-level lookup for all three came back `undefined` in every deployment, the fail-closed transform gave `false` for every required flag, and G5 could not pass. The pre-fix runbook narrative "one server switch" was itself a fixture-drift artifact: because every test asserted against fixtures the desktop authored, five thousand tests could agree on a wire vocabulary that no PrintFarmer server has ever emitted. **Lesson: when running the gate chain against a real server for the first time, don't just check "does the required flag pass?" — capture the _raw JSON_ and diff its field names against the alias map. A `false` returned by a flag-lookup that resolves to `undefined` is indistinguishable from an honest `false` at the transform layer, but is a completely different bug.**
- 2026-08-21 Round 2: `RemoteOperatorFeatureFlags` is `.passthrough()` with only `offlineWriteReplayEnabled` declared. The other nested block fields (attention, filamentCoverage, guidedSwap, multiSlotFallback, shiftPlan, printedPartsInventory, nativePush) are ignored by desktop calibration but pass through negotiation without complaint. This is the correct shape for a nested capability block the server owns — declare only what you read, passthrough the rest. Don't declare a full `RemoteOperatorFeatureFlags` mirror; every unread field you declare is a maintenance burden you owe the server for no functional gain.
- 2026-08-21 Round 2: The error-envelope fix was two problems disguised as one. (1) The `RemoteCalibrationProblemDetails` schema had `errorCode ?? code ?? type` as its resolution order; the server actually sends `error`. (2) `JobQueueController` sends `application/json`; `GcodeFilesController` sends `text/plain` on 404. Fixing (1) alone would still leave 404s throwing at `JSON.parse`. Sniffing `content-type` before `JSON.parse` is the right shape, and doing it in both `statusError()` and a dedicated `readJobErrorEnvelope()` keeps the 409/422 branches from re-parsing the same body twice with different rules.
- 2026-08-21 Round 2: When Round 1 recommended surfacing server-side gate reasons through IPC, the schema choice mattered more than the code. `CalibrationServerUnavailableReason.parse({ feature, code, message })` mirrors the exact server DTO and reserves 64 slots — the same order of magnitude the server can produce for a split deployment. A single-string flatten (like turning `['slicer_registry_unavailable','artifact_source_unroutable','split_routing_unavailable']` into `"slicer_registry_unavailable, artifact_source_unroutable, split_routing_unavailable"`) is what the pre-fix desktop was doing implicitly by refusing to surface the field, and it made every split-mode refusal look like the same undifferentiated error. When Dallas designs the operator narrative, he can now render each reason with its own actionable copy. **Lesson: when moving a data shape across a trust boundary, mirror it; do not summarize it. Summarization at the wire is a permanent loss of resolution.**
- 2026-08-21 Round 2: The runbook-references test tokenized `operatorFeatures.offlineWriteReplayEnabled` as a "log component" because its regex matches any camelCase dotted identifier. Fixing it by allow-listing dotted values from `Object.values(CALIBRATION_FLAG_SOURCES)` was correct — but the deeper lesson is: **when a test lints doc references, its tokenizer and its allow-list must both derive from production source**, or the lint drifts. A test that hard-codes what "counts" as a valid log component will always disagree with production the moment production adds a new class of dotted identifier. This is the same self-referential-fixture antipattern that hid the alias-map bug.
- 2026-08-21 Round 2 CORRECTION: I mis-fixed G5 by taking the coordinator's briefing at face value. The briefing said the desktop's internal flag names "do not exist on the wire" and that the alias map was wrong. Both statements were true in isolation but together implied a category error: the internal names AREN'T supposed to exist on the wire — that's why the alias map exists. If I had walked the alias map's actual bindings against the actual live payload before typing a single character, I would have seen the pre-fix map resolves all three required flags TRUE, not undefined. Instead I trusted the diagnosis. **Lesson: for any "the mapping is wrong" claim, the minimum evidence is a table with three columns — internal name, aliased source-of-truth field, resolved live value — filled in from the actual wire capture. If any resolved value is `undefined`, the mapping is wrong; if all resolve to the expected shape, the mapping is right and the bug is elsewhere. Do not proceed to rewrite the mapping without that table.** This is the exact predicate-vs-control discipline `.squad/known-lying-commands.md` was written to install, and I walked past it.
- 2026-08-21 Round 2 CORRECTION: The infrastructure improvements from the mis-fix — `readFlagBackingField` dotted-path resolver, `setCalibrationFlagBackingField`/`unsetCalibrationFlagBackingField` test helpers, `RemoteOperatorFeatureFlags.passthrough()` schema, declared `calibrationContextEnabled`/`calibrationEventsEnabled`/`operatorFeatures`/`unavailableReasons` fields — are worth keeping even when the mapping revert removes the specific use case. `readFlagBackingField` in particular closes a class of bug (flat comparator blind to nested value) that is invisible in tests written against a flat comparator, and once seen cannot be unseen. **Rule: when reverting a mis-diagnosed root-cause "fix", keep the infrastructure changes that make the _class of bug_ easier to see next time, even if this specific instance was diagnosed wrong.** The specific decision doesn't have to be right for the diagnostic capability to be worth installing.
- 2026-08-21 Round 2 CORRECTION: `docs/API.md` and `PlatformCapabilitiesDto.cs` XML docs are decisive over any live "capture-driven" reading. Bishop's `CalibrationCapabilityService.cs:203-205` (hardcodes three sibling `Enabled` flags to false, one assignment each, no config path) proved the semantic gap between `CalibrationSyncEnabled` (change-feed/sync, at `PlatformCapabilitiesDto.cs:47-48`) and `CalibrationEventsEnabled` (a _distinct_ unimplemented future event-streaming subsystem, at `:71-72`). If the coordinator's briefing had cited the DTO XML doc, I would have caught the category error immediately. **Rule for future briefings I receive: if a briefing claims a mapping is wrong, the minimum citation is the server DTO's own XML doc for both the old and new source fields. Anything less is a claim, not evidence.**
- 2026-08-21 Round 2 CORRECTION: `CalibrationQueueState` in `src/shared/ipc.ts` was a Zod schema that nothing populated and nothing consumed — an orphan, but one whose fields (`printStartAllowed`, `printStartBlockedReason`) were named in `docs/runbooks/stale-dispatch-lease.md`. Deleting the orphan and moving its two fields (optional/nullable) onto `CalibrationQueueJobState.passthrough()` — the schema actually used by `getCalibrationQueueState` — was the correct fix: the runbook still name-resolves through `CONTRACT_SCHEMAS` membership, and any server that emits these fields on a job DTO now has explicit typed positions rather than being merely passed-through. **General lesson: an orphan schema whose fields are documented elsewhere is a rot smell, not just tidy dead code. Its existence tricks doc-reference checkers into thinking the docs are covered; its absence would have flagged the doc as unbacked.**
- 2026-08-21 Round 2 CORRECTION: The verdict I gave the coordinator on the (a) DI-mis-registration vs (b) genuinely-not-implemented question was structurally different from a "what do the flags say" answer: it required correlating the DESKTOP's dispatch path (`POST /api/job-queue/{gcodeFileId}/start` — a general-queue endpoint, not calibration-specific) with the SERVER's `calibration.queueIntegrationImplemented: false` self-report, and reasoning about whether that self-report protects a code path the desktop actually uses. My verdict was (a) with a specific caveat: the desktop does not need calibration-specific queue integration to dispatch a print — it only needs the general job queue, which is implemented — but I cannot decisively rule out that `queueIntegrationImplemented` protects a path the desktop implicitly depends on. **Lesson: architectural questions of the form "is X reachable through this system's current shape?" need to be answered by tracing the specific code path the caller uses, not by summing all the "implemented" self-reports. A false all-summing verdict looks robust and is not.**
