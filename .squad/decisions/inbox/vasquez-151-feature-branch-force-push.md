# #151 decided: no server-side ruleset for feature branches today; the tripwire is the control against this decision going stale

**By:** Vasquez, per the squad:vasquez routing on #151 and the explicit request in that issue's third Ripley comment ("Name one, or decide it here in a comment.").

**Decision.** Do not adopt a repository ruleset — blanket or ref-pattern-scoped — covering feature branches. `#149`'s client-side guard (`push:force`, the pre-push hook) remains the only control on feature branches until the trigger condition below fires. This closes the two open questions #151 asked and leaves the two #111 decisions undisturbed, exactly as #151 asked not to reopen them.

## The evidence this rests on, and where it already lives

I did not re-measure. #151's own comment thread (Ripley, three comments, 2026-08-03/04) already ran the arms this decision needs, each with a positive control:

- A push allowlist with an empty entry list **does not bind** the sole admin account — `enforce_admins` on or off. Verified twice, independently, against two different mechanisms (branch-protection restrictions and, separately, a ruleset's `bypass_actors: []`), because an admin exemption and an allowlist that has nothing to discriminate produce the identical observation and only two independent instruments separate them.
- A repository ruleset carrying `non_fast_forward` with `bypass_actors: []` **does bind** the same account: force-push refused `GH013`, ordinary fast-forward accepted, and the refusal is attributable to enforcement specifically because flipping `enforcement` to `disabled` (one field, arm C) let the identical rewrite through.
- The ruleset's `refs_name.include` pattern matches branches **created after** the ruleset was written (arm D: a branch created post-hoc under a wildcard include had its rewrite refused). This is the property per-branch protection objects cannot supply and is the only reason a ruleset is the right instrument shape at all.
- `npm run push:force` (from #149) resolves to `--force-with-lease=<ref>:<sha> --force-if-includes` — a genuine force-push. It is exactly the operation a `non_fast_forward` rule refuses. **The server-side rule cannot discriminate the audited rewrite `push:force` performs from the destructive one #81 recorded.** With one collaborator, `bypass_actors` and "disable the rule" are the only two states, and both return the ruleset to decoration.

Live re-read at the time of this decision (`gh api repos/OlyForge3D/PrintFarmerDesktop/branches/development/protection`, `/rulesets`, `/collaborators`): `allow_force_pushes.enabled = false`, `enforce_admins.enabled = false`, one ruleset (`20361532`, `development merge queue`, `enforcement: disabled`, scoped to `refs/heads/development` only), one collaborator (`jpapiez`, admin). Unchanged from #151's 2026-08-03 read except the ruleset row, which #151's own re-run had already caught and priced as not reaching feature branches.

## Why each option on the table is rejected

**Option 2 (broad `non_fast_forward` ruleset, `bypass_actors: []`) — rejected.** This is the arm B measurement above: it refuses `push:force` on the day it's enabled, for the only account that can push. That is a real, paid cost — not hypothetical — against a workflow `.squad/skills/git-workflow/SKILL.md` documents as the repair path for a broken PR stack. No benefit accrues to offset it: the account that would be newly restrained is the same account already exempt from `development`'s equivalent rule via `enforce_admins: false`, so this option protects nothing that isn't already reachable by the same actor bypassing it via `enforce_admins` logic on the *next* rule they'd hit.

**Option 3 (same ruleset, `jpapiez` added to `bypass_actors`) — struck outright,** per Ripley's own recommendation in #151. With one collaborator, naming them as the bypass actor is bypass for everyone who can push. It would read as an enforced control in the GitHub UI (`✓ non_fast_forward: active`) while restraining nothing — worse than Option 1, because Option 1 does not claim to be enforced and this would.

**Option 4 (ruleset scoped to a review-branch ref pattern, entered by rename at review start) — considered and not adopted now, for a reason not yet on record: the branch-naming convention it depends on does not exist in this repository.** Checked directly (`git branch -a`, current HEAD included): active branches are named `dev/jpapiez/*` (the majority), `dallas-*`, `agent/pf-*`, and others, with no consistent `squad/**` or `review/**` prefix in practice despite this issue's own implementation branch being asked to use one. Scoping a ruleset to a pattern that must be entered by a manual rename adds exactly the failure mode this issue exists to close — a step a human (or a session) can forget, which then fails silently and open, with nothing in the UI distinguishing an unrenamed branch from one that was never meant to be protected. That is the same class of failure as the bypassable `--no-verify` escape #151 already counts as the known weak point of Option 1, not an improvement on it. It remains available to reconsider if a naming convention is separately adopted and enforced (e.g. by CI), but is not worth the operational cost against a single-collaborator repository today.

**Option 1 (status quo: no ruleset, rely on #149's client-side guard) — adopted.** Its documented weakness stands and is accepted rather than papered over: `--no-verify` bypasses it, and it binds only clones where `npm install` has run — the exact profile of the second-session actor in both #81 incidents (PR #78: `254fd9e`, `b9f1dea`; PR #68). Both incidents already happened under this option and it was not free. It is adopted anyway because every alternative available today either (a) costs a real, paid capability with no offsetting protection (Option 2), (b) is decoration masquerading as enforcement (Option 3), or (c) trades one silent-failure mode for another that has no existing convention behind it (Option 4).

## The control against this decision going stale is already built, not newly added here

#151's revisit trigger — "the moment a second collaborator or any non-admin automation account exists" — was already converted from a paragraph into a tripwire in PR #386 (`e1448d70`, `feat(security): make #151's revisit trigger a tripwire instead of a paragraph`): `scripts/check-protection-assumptions.mjs`, run via `npm run check:protection-assumptions`, re-reads `branches/development/protection`, `/rulesets`, `/branches?protected=true`, and `/collaborators` live and fails when any of them has moved off the values this decision and #111 rest on — explicitly including `rulesetCoversFeatureBranches()`, which fires the day a ruleset with an `enforcement: active` state reaches a ref outside `development`. This decision does not duplicate that tripwire; it is the decision the tripwire exists to protect. When it fires, re-read this entry and #111 together, per the tripwire's own violation message.

## What this does not reopen

`enforce_admins: false` and declining a required approving review remain #111's decisions, unchanged and not revisited here. This entry closes #151's two open questions (ruleset-for-feature-branches, and the #149 conflict) without touching either.
