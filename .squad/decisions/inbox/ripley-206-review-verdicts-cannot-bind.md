# #206 decided: binding reviews cannot work in this configuration; nothing mechanical gates a PR carrying live blockers today, and arming one is worse than not

**By:** Ripley, per the `squad:ripley` routing on #206 and Ralph's 2026-08-08 dispatch, which asked for exactly two things: the recorded finding that binding reviews cannot work here, and a decision on what — if anything — gates a PR carrying live blockers given `reviewDecision` can never move off empty.

**Decision.** Binding reviews (`APPROVE` / `REQUEST_CHANGES`) cannot work in this repository's current configuration, and the mechanism is determined, not inferred. Nothing mechanical gates a PR carrying live COMMENT-pinned blockers today; this is adopted deliberately, as restraint by choice with the alternatives named and priced, not as an unstated default. The one durable, mechanical artifact this issue names is a non-blocking coverage report — visibility, not a gate — run by hand today (`scripts/check-review-head-coverage.mjs`, from #280); wiring it into CI non-blockingly was drafted and validated but not pushed in this session (see below), because arming any verdict-shaped or blocker-scan-shaped check as a merge requirement would repeat a trap this repository has already paid for twice on adjacent issues (#151, #280).

## The cause, already measured in #206's own thread — not re-derived here

- `POST /pulls/N/reviews {"event":"APPROVE"}` → `422 {"errors":["Review Can not approve your own pull request"]}`; the identical shape for `REQUEST_CHANGES`. Only `COMMENT` returns `201`. Reproduced twice, 15 hours apart, on two different PRs (#209 and a second, per the issue body).
- Population-complete measurement, not a sample: **178 PRs examined, 45 reviews, 0 `APPROVED`, 0 `CHANGES_REQUESTED`, 1 collaborator (`jpapiez`, admin).** Every review this repository has ever produced is `COMMENTED`.
- The self-review restriction is the correct and sole explanation: author and reviewer are the same account on every PR that exists or can exist here, `gh api user` confirms the identity, and `COMMENT` landing `201` on the same endpoint with the same token rules out a token-scope or repository-setting cause.

## Why binding reviews cannot be made to work here

A distinct second principal (`github-actions[bot]`, via `GITHUB_TOKEN`, already holding `pull-requests: write` in `lift-sequencing-hold.yml`) is not blocked by the self-review restriction and could submit a `REQUEST_CHANGES` that lands and would move `reviewDecision` off empty. So self-review is precisely what is structurally impossible for the sole human collaborator — not a claim that no principal anywhere could ever produce a binding-looking verdict. **The bot route is declined on its merits, not for lack of an account, because "moving `reviewDecision` off empty" and "gating anything" are different claims here:**

Live-read via GraphQL at the time of this decision (`branchProtectionRules` on `development`, which is the authoritative source — see the control note below): `requiresApprovingReviews: false`, `requiredApprovingReviewCount: null`, `dismissesStaleReviews: false`, `isAdminEnforced: false`. **No approving-review requirement of any kind is currently configured on `development`, from anyone.** A bot-submitted `REQUEST_CHANGES` would therefore be exactly as advisory as every `COMMENT` review already is: it would populate `reviewDecision` and read as a real verdict in the GitHub UI, while `mergeStateStatus`/`mergeable_state` would remain governed only by the required status checks and `enforce_admins: false`, unaffected by it either way. That is the same shape #151 struck outright for its own "add `jpapiez` to `bypass_actors`" option, and the same shape #204 was withdrawn to avoid: a control that reads as enforced and cannot fire. Recording an available-but-declined option is the honest version of this decision; treating it as unavailable would not be.

**Control note, because this is exactly the kind of claim this repository has been burned by before:** the REST sub-resource `GET /branches/development/protection/required_pull_request_reviews` returned `required_approving_review_count: 1, dismiss_stale_reviews: false` on repeated re-reads at the same time as the GraphQL read above — a live contradiction between two API surfaces describing the same setting. GraphQL's `branchProtectionRules` was taken as authoritative and cross-checked against actual behaviour: `gh pr view` on the two open PRs at the time (`#595`, `#599`) shows `reviewDecision: ""` and REST `mergeable_state: "clean"` / `"blocked"` respectively, with the `#599` block attributable entirely to failing/in-flight status checks and neither PR showing `REVIEW_REQUIRED` — which is the value GitHub sets when an approving-review count is actually enforced. The REST sub-resource reading is treated as stale/inconsistent rather than current fact, and is recorded here rather than silently discarded, because the same class of divergence is exactly what the existing tripwire (`scripts/check-protection-assumptions.mjs`) would miss: it only reads the parent `/protection` object, which omits `required_pull_request_reviews` entirely when the requirement isn't active, so its `reviewCount !== undefined` check never fires on this repository's current configuration either way.

The other candidate — set `required_approving_review_count: 1` on `development` — was correctly identified in the issue thread as a deadlock trap, not a fix: the sole account can never submit an `APPROVE` (422), so the branch could never again accumulate the approval it would demand.

## What gates a PR with live blockers instead: nothing mechanical, today, by choice

A verdict-shaped or blocker-scan-shaped required check is not buildable with the instruments this repository has:

- **A check reading the PR body** for a blocker marker is not re-armed by a body edit unless its workflow explicitly subscribes to `pull_request: types: [..., edited]` — the exact defect #436 fixed generally (`scripts/check-body-edit-triggers.mjs`). That fix makes body-derived guards re-run on edit; it does not create a way to _derive a blocking verdict_ from a body, because the acceptance criteria for such a marker would still have to be self-attested by the same single account that authored the PR.
- **A check reading issue/PR comments** for blocker language is structurally worse: posting a comment fires `issue_comment`, a different event on a different trigger than `pull_request`, and a required status context is matched against the head commit's check runs. A comment produces no new head, so there is no re-run point bound to the commit a merge would certify — a required check built on it could pass while certifying a revision of the conversation that no longer reflects the live state.
- Both problems are independent of the review-verdict problem above and would exist even if `reviewDecision` were populated, because GitHub's own review object is the only construct that binds a verdict to a `commit_id` at all (`scripts/check-review-head-coverage.mjs`, built for #280, exists specifically because comments and bodies don't have that binding).

**Adopted:** rely on restraint — a squad member (or the same account acting as reviewer) chooses not to merge over a live blocker — as a stated, deliberate choice, not an unexamined default. This is the acceptance criteria's own explicitly sanctioned second outcome ("a recorded decision to run on restraint _by choice_, with the alternatives named, is acceptable").

## The one mechanical artifact this decision names, and why it stays a reading

`scripts/check-review-head-coverage.mjs` (from #280) already answers a narrower, answerable question: does _any_ review — `COMMENT` included — carry a `commit_id` matching the PR's merged head. Unlike an approval requirement, `COMMENT` reviews land here (`201`), so this signal is obtainable without deadlocking anything. #280 built it as a human-run visibility tool, invoked deliberately rather than on a schedule, precisely because arming it as a required check would be the trap named below.

A CI-wired, non-blocking variant of the same script (`continue-on-error: true`, explicitly excluded from required status contexts) was drafted for this decision and validated locally, but could not be pushed from this session: the CLI's git credential path is pinned to an OAuth App token without `workflow` scope, so any push that creates or modifies a file under `.github/workflows/` is rejected by GitHub before it reaches this repository's own review process. That is a limitation of this session's tooling, not a finding about the repository, and it is recorded here rather than routed around, because silently dropping it without a note would misrepresent what was actually verified. The script itself is unchanged and remains available to run by hand (`npm run check:review-coverage -- <PR number>`); wiring it into CI non-blockingly is left as follow-up work for a session (or a maintainer) that can push workflow-scope changes, not reopened as a design question — the shape (informational, non-required) is decided, only the delivery mechanism is outstanding.

This is not offered as a gate and must not become one, whether run by hand today or wired into CI later. Arming it as a merge requirement would reintroduce the exact trap named above and struck for #151's Option 3: a control that reads as enforced in the GitHub checks list and cannot fire, because it measures "a review comment exists at this SHA," not "the blockers in it were resolved" — the same gap between signal and control this issue exists to close, one layer down.

## Why #151 is "the same decision" and does not need to be reopened here

#206's own body names #151 as resolving to the same decision. #151 (closed via PR #593) found that identity-based server-side controls (review approval requirements, push allowlists) do not bind a single-principal squad, while content/operation-based ones (a `non_fast_forward` ruleset) do — and even a working operation-based control was declined because it broke a legitimate workflow (`push:force`) with no offsetting protection, the identical cost/benefit shape used above to decline the bot-review option. This entry applies the same reasoning to the review layer specifically: identity-based (`reviewDecision`, required approvals) cannot bind here; the one instrument that can be built honestly (`commit_id`-bound coverage) is content/operation-based, and it stays a reading rather than a gate for the same reason #151 declined its own available-but-decorative option.

## What this does not reopen

Does not revisit #111 (`enforce_admins: false`, no required approving review) or #151's ruleset question — both remain as decided.

## The trigger to revisit

The moment a second reviewing principal exists whose verdict is not structurally inert — i.e., `required_approving_review_count` can move above 0 without deadlocking every PR — re-open this decision and #151 together, per #151's own trigger clause.
